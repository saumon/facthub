# Data Model: Next Fact by Client

**Phase**: 1 — Design  
**Date**: 2026-05-24  
**Branch**: `002-next-fact-client`

## Entities

---

### Client

Represents an eligible API consumer allowed to call the sequential next-fact endpoint.

| Field | Type | Constraints | Description |
| ----- | ---- | ----------- | ----------- |
| `id` | integer | PK, auto-increment | Internal primary key for admin management |
| `client_identifier` | string | NOT NULL, UNIQUE, immutable after creation | Opaque public identifier generated by the system and used by API clients |
| `last_fact_id` | integer | nullable | Numeric identifier of the last fact served to this client; nullable before first retrieval |
| `created_at` | datetime | NOT NULL | Record creation timestamp |
| `updated_at` | datetime | NOT NULL | Last change timestamp |

**Validation rules**:

- `client_identifier` must be present and unique.
- `client_identifier` is generated by the system on create and is not edited through the admin UI.
- `last_fact_id` may be null for a newly created or reset client.

**Design note**: `last_fact_id` is intentionally stored as a plain integer cursor rather than a foreign
key so the system can continue correctly even if the previously served fact is deleted.

**State transitions**:

```text
[Created, no progress]
      │ first successful next call
      ▼
[In progress at fact N] ──next call──▶ [In progress at fact N+1 or wrapped fact]
      │
      ├──reset──▶ [Created, no progress]
      └──delete──▶ [Removed / no longer eligible]
```

**Indexes**:

- Primary key on `id` (implicit)
- Unique index on `client_identifier`

---

### Fact Sequence

Represents the ordered retrieval space used by the next-fact endpoint. This is a derived business
concept built from the existing `facts` table.

| Property | Value |
| -------- | ----- |
| Source | Existing `facts` records |
| Canonical order | Ascending `facts.id` |
| Entry point | Lowest available fact id |
| Wrap behavior | After the highest available fact id, restart at the lowest available fact id |
| Mutation effect | Newly created facts become immediately eligible at their canonical position |
| Deletion effect | Deleted facts disappear from future retrieval; clients continue from the next available fact id greater than their stored cursor, or wrap |

**Business rules**:

- The same fact should not be re-served to a client until the client has traversed all currently
  available facts, unless only one fact exists.
- If `last_fact_id` points to a removed fact, the system still treats that numeric value as the anchor
  for finding the next available fact in ascending order.

---

### Admin Session (existing reused entity)

The feature reuses the existing Devise-backed authenticated admin session from feature 001.

| Property | Description |
| -------- | ----------- |
| Owner | `Admin` model instance |
| Guard | `authenticate_admin!` via `Admin::BaseController` |
| Scope | Required for all client management pages and actions |
| Expiry | Existing Devise timeout behavior remains unchanged |

## Entity Relationships

```text
Admin Session ──authorizes──▶ Client management UI/actions

Client ──stores cursor as last_fact_id──▶ Fact Sequence

Fact Sequence ──is derived from──▶ Fact (existing table)
```

There is no required persisted join table between clients and facts in this feature scope.

---

## Integrity Rules Summary

| Rule | Enforced by |
| ---- | ----------- |
| Client identifier is generated, unique, and opaque | Model callback/validation + DB unique index |
| Client management requires authentication | `Admin::BaseController` with `authenticate_admin!` |
| New client starts with no progression | `last_fact_id = null` on create |
| Reset returns client to initial state | Reset action clears `last_fact_id` |
| Deleted client can no longer call next-fact | Client record removal + API lookup failure |
| Fact ordering is canonical by ascending fact id | Query ordering in progression resolver |
| Deleted prior fact does not corrupt progression | Integer cursor semantics + next-available query |
| Same-client concurrent calls advance exactly once each | Transactional progression update in resolver |
